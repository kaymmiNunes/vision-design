# Roteiro de Produção do Projeto  
**Turma:** 3º A  
**Grupo:** 3  
**Projeto:** **Vision Design**

---

## Apresentação do projeto ao grupo

Grupo, a proposta de vocês é criar um sistema chamado **Vision Design**, voltado para o **gerenciamento de pedidos e projetos de design**. A ideia é organizar melhor o atendimento, o briefing, as etapas de produção, os prazos, as revisões e as entregas finais. Além disso, o projeto tem um diferencial importante: ele também pensa em atender **pequenos empreendedores, escolas e iniciativas sociais**, que muitas vezes precisam de materiais visuais, mas não têm acesso a processos profissionais bem organizados.

O mais importante durante o desenvolvimento é não tentar criar um sistema muito complicado logo no início. O melhor caminho é construir uma aplicação **simples, clara, útil e funcional**, que resolva o problema principal e que possa ser desenvolvida em sala de aula com organização.

Vocês não precisam começar criando um sistema completo como os usados por empresas grandes. O ideal é fazer uma versão escolar, com o essencial bem definido: cadastro, registro de pedidos, acompanhamento de etapas e visualização das entregas. É melhor apresentar uma aplicação simples funcionando do que planejar muitas funções e não conseguir concluir até agosto.

Durante a produção, o grupo precisa dividir tarefas, registrar decisões, revisar o que foi feito e salvar o projeto no GitHub. Isso ajuda a não perder arquivos, evita confusão e mostra a evolução do trabalho.

## 1. Análise simples da proposta do projeto

O projeto de vocês pretende criar um **sistema para organizar pedidos e projetos de design**. Em vez de anotar tudo em papel ou em mensagens soltas, a ideia é reunir informações em um só lugar para facilitar o trabalho de quem recebe o pedido e de quem acompanha a produção.

### O que esse projeto pretende resolver
Muitas demandas de design são feitas de forma desorganizada: o cliente pede algo, depois muda o pedido, esquece prazo, não manda referência, e o responsável pelo design acaba ficando perdido. Isso gera atraso, retrabalho e falhas na comunicação.

### Problema principal
O problema principal é a **falta de organização no registro, acompanhamento e entrega de pedidos de design**.

### Objetivo geral da aplicação
O objetivo do sistema é **organizar os pedidos e projetos de design**, ajudando no controle de informações, etapas, revisões, prazos e entregas.

### Utilidade do sistema no dia a dia
Esse sistema pode ajudar a:
- cadastrar clientes ou instituições;
- registrar pedidos de design;
- guardar briefing e referências;
- acompanhar em que etapa está cada projeto;
- controlar prazo de entrega;
- registrar revisões;
- organizar entregas finais.

### Público-alvo
O público-alvo pode ser:
- pequenos empreendedores;
- escolas;
- iniciativas sociais;
- pessoas ou grupos que precisam solicitar artes, cartazes, banners, posts ou materiais visuais;
- estudantes ou equipes que prestam serviços de design.

### Possíveis funções principais do sistema
O sistema pode incluir:
- cadastro de clientes, instituições ou solicitantes;
- cadastro de pedidos de design;
- descrição do briefing;
- campo para referências visuais;
- registro de prazo;
- status do projeto;
- acompanhamento por etapas;
- histórico de revisões;
- organização da entrega final.

## 2. Planejamento geral até agosto

Para que o projeto fique pronto até agosto, o ideal é desenvolver o sistema em partes. Como o grupo ainda está em processo de aprendizagem, o melhor caminho é sair da organização da ideia, passar pela estrutura do sistema e só depois chegar na primeira versão funcional.

Cada etapa foi pensada para **2 aulas de 50 minutos**.

### Ordem geral de construção
A ordem recomendada é esta:

1. entender a proposta e o problema do projeto;  
2. definir as funções principais do sistema;  
3. organizar requisitos;  
4. escolher tecnologias adequadas;  
5. planejar a estrutura das telas e dos arquivos;  
6. criar o esqueleto da aplicação;  
7. montar a primeira versão funcional;  
8. salvar e publicar no GitHub;  
9. revisar e melhorar o sistema;  
10. preparar a entrega final e a apresentação.

### Visão do desenvolvimento até agosto
A sequência pode seguir este ritmo:

**Abril:** entendimento da proposta, planejamento, requisitos e estrutura  
**Maio:** montagem das telas e da base do sistema  
**Junho:** interações, formulários e primeira versão funcional  
**Julho:** revisão, melhorias e GitHub  
**Agosto:** versão final e apresentação

## 3. Levantamento de requisitos

### O que são requisitos
Requisitos são as necessidades do projeto. Eles mostram o que o sistema precisa fazer e quais características ele precisa ter.

### Diferença entre requisitos funcionais e não funcionais
**Requisitos funcionais** são as funções do sistema.  
Exemplo: cadastrar cliente, registrar pedido, exibir status do projeto.

**Requisitos não funcionais** são qualidades do sistema.  
Exemplo: ser organizado, fácil de usar, ter linguagem clara e funcionar corretamente.

### Quais requisitos esse projeto provavelmente terá
Como o projeto é um sistema de gerenciamento, ele precisa registrar informações, organizar dados e permitir o acompanhamento dos pedidos de forma clara.

### Requisitos funcionais
- O sistema deve permitir cadastrar clientes, instituições ou solicitantes.
- O sistema deve permitir registrar pedidos de design.
- O sistema deve permitir armazenar briefing do projeto.
- O sistema deve permitir registrar referências visuais ou observações.
- O sistema deve permitir definir prazos.
- O sistema deve mostrar o status do projeto.
- O sistema deve permitir acompanhar etapas do trabalho.
- O sistema deve permitir registrar revisões.
- O sistema deve organizar a entrega final.
- O sistema pode permitir filtrar projetos por andamento.

### Requisitos não funcionais
- O sistema deve ter interface simples.
- O sistema deve ser fácil de usar por iniciantes.
- O sistema deve ter organização visual clara.
- O sistema deve funcionar em navegador comum.
- O projeto deve ter arquivos organizados.
- O sistema deve ser possível de concluir até agosto.
- O conteúdo das telas deve ser compreensível.
- O sistema deve evitar excesso de informações na mesma tela.

## 4. Tecnologias indicadas

Para esse projeto, a melhor escolha é usar tecnologias simples para construir uma aplicação web básica.

### HTML
HTML serve para montar a estrutura das páginas: títulos, formulários, tabelas, botões e campos.

### CSS
CSS serve para cuidar da aparência do sistema: cores, organização, espaçamento, layout e leitura.

### JavaScript
JavaScript serve para criar interações, como:
- cadastrar pedidos em tela;
- mudar status do projeto;
- exibir listas de tarefas;
- mostrar mensagens ao usuário;
- simular armazenamento local.

### localStorage
O `localStorage` pode ser usado para guardar dados simples no navegador, como clientes e pedidos, sem precisar de banco de dados mais avançado. Isso é uma boa alternativa escolar.

### GitHub
GitHub serve para guardar o projeto, registrar a evolução e organizar o trabalho em grupo.

### Tecnologias recomendadas para este projeto
- HTML
- CSS
- JavaScript
- localStorage
- Git e GitHub
- VS Code ou editor semelhante

### Alternativa simples para ambiente escolar
Em vez de usar banco de dados e servidor logo no começo, o grupo pode fazer um **sistema web simples no navegador**, com cadastro funcionando localmente. Essa versão já demonstra bem a ideia do projeto.

### Por que essas tecnologias são boas para esse projeto
Porque são:
- mais acessíveis para iniciantes;
- simples de testar;
- suficientes para uma primeira versão funcional;
- adequadas ao tempo disponível;
- boas para montar protótipos e sistemas escolares.

### Exemplo de `js/clientes.js`

```javascript
const formCliente = document.getElementById("formCliente");
const nomeCliente = document.getElementById("nomeCliente");
const contatoCliente = document.getElementById("contatoCliente");
const listaClientes = document.getElementById("listaClientes");

let clientes = JSON.parse(localStorage.getItem("clientes")) || [];

function mostrarClientes() {
  listaClientes.innerHTML = "";

  clientes.forEach((cliente) => {
    const item = document.createElement("li");
    item.textContent = `${cliente.nome} - ${cliente.contato}`;
    listaClientes.appendChild(item);
  });
}

formCliente.addEventListener("submit", function(evento) {
  evento.preventDefault();

  const novoCliente = {
    nome: nomeCliente.value,
    contato: contatoCliente.value
  };

  clientes.push(novoCliente);
  localStorage.setItem("clientes", JSON.stringify(clientes));

  nomeCliente.value = "";
  contatoCliente.value = "";

  mostrarClientes();
});

mostrarClientes();
```

## 8. Orientação de commit no GitHub

### O que é commit
Commit é um registro de uma mudança feita no projeto. É como salvar uma etapa importante do trabalho com uma mensagem explicando o que foi feito.

### Por que usar GitHub
O GitHub ajuda a:
- guardar o projeto online;
- evitar perda de arquivos;
- mostrar a evolução do grupo;
- organizar o trabalho.

### Como criar um repositório
1. Entrar no GitHub.
2. Clicar em **New repository**.
3. Escolher um nome, por exemplo: `vision-design`.
4. Criar o repositório.
5. Copiar o link do repositório.

### Como organizar os arquivos antes de enviar
Antes de enviar:
- conferir os nomes dos arquivos;
- deixar tudo nas pastas certas;
- remover arquivos repetidos;
- garantir que o sistema funciona localmente.

### Exemplo de comandos básicos

```bash
git init
git add .
git commit -m "Estrutura inicial do projeto"
git branch -M main
git remote add origin LINK_DO_REPOSITORIO
git push -u origin main
```

### Comandos para novas atualizações

```bash
git add .
git commit -m "Adiciona cadastro de clientes e pedidos"
git push
```

### Exemplos de mensagens de commit
- `Estrutura inicial do projeto`
